## 执行状态机（Execution State Machine, ESM）— v1.7.0 架构核心

> **两次审计全局洞察与深层根因**
>
> v1.6.3 双宿主审计（评分 44–65/100）暴露了 5 个执行死角：.fbs 未初始化、Chapter Brief 静默跳过、模型知识无标注、S2.5 行动计划无核销、author-meta 成孤岛。v1.6.7 追踪报道审计又暴露了一组更深层的问题：入口偏移、检索过度不起稿、状态推进快于文稿落地、中间产物缺失、交付延迟。
>
> 将两次审计的所有执行偏差放在一起分析，它们**共享三个结构性深层原因**：
>
> **深层原因一：规范是「规则的堆叠」而非「状态的感知」**。每次审计发现问题后，修复方式是加入新的禁令/门禁/检查点——但模型在运行时需要同时 hold 住所有禁令（v1.6.7 超 1900 行），越堆越容易遗漏。模型缺乏「我当前在哪个状态 → 下一步该做什么」的运行时自感知。
>
> **深层原因二：体裁适配是「临场口头改写」而非「编译时分发」**。S0-S6 是为 A 级书籍设计的，B/C 级通过在 A 级上打补丁（S0-lite、S1 简化、S5-lite）适配，模型需在脑中 hold 完整 A 级流程然后做减法——极不可靠。
>
> **深层原因三：瀑布假设与螺旋实践的冲突**。Skill 假设「调研→结构→写作」是严格串行的，但真实写作是螺旋式的（写→发现缺口→补搜→续写）。v1.6.7 加了「局部先写」，但它作为独立规则插入而未改变底层瀑布假设。
>
> **本节的设计目标**：引入一个轻量执行状态机，让模型在每个时刻只需关注「当前状态 → 出口条件 → 下一状态」，而非扫描全部禁令。状态机不替代下文的详细规则，而是为它们提供**执行调度层**。

### ESM 状态定义

```
┌─────────────────────────────────────────────────────────────────────┐
│                    FBS-BookWriter 执行状态机                         │
│                                                                     │
│  ┌──────┐    ┌──────┐    ┌────────┐    ┌──────┐    ┌──────┐         │
│  │ IDLE │───▶│INTAKE│───▶│RESEARCH│───▶│ PLAN │───▶│WRITE │──┐      │
│  └──────┘    └──────┘    └────────┘    └──────┘    └──────┘  │      │
│                              ▲            │           │      │      │
│                              │            │           ▼      │      │
│                              │      ┌──────────┐  ┌──────┐  │      │
│                              └──────│WRITE_MORE│◀─│REVIEW│  │      │
│                                     └──────────┘  └──────┘  │      │
│                                                       │      │      │
│                                                       ▼      ▼      │
│                                                   ┌──────────┐     │
│                                                   │ DELIVER  │     │
│                                                   └──────────┘     │
└─────────────────────────────────────────────────────────────────────┘
```

### ESM 状态转换表（全体裁通用，出口条件按体裁分级自适应）

| 状态 | 含义 | A 级出口条件 | B 级出口条件 | C 级出口条件 | 强制产出物 |
|------|------|-------------|-------------|-------------|-----------|
| **IDLE** | 等待触发 | 品牌/触发词命中 | 同左 | 同左 | 无 |
| **INTAKE** | 任务锁定 | 主题+体裁+读者确认 | 主题+体裁确认（合并一轮） | 主题确认 | 主题声明 |
| **RESEARCH** | 调研采证 | S0 三项+S0-E素材 | S0-lite（时间戳+主题+1轮竞品扫描） | ≥1 次检索 | search-ledger 登记 |
| **PLAN** | 结构锁定 | S1+S2+S2.5 全流程 | 证据台账+MVD+Report Brief | 无独立 PLAN（直接成文） | Brief 存盘 |
| **WRITE** | 成文 | Chapter Brief→逐章成文 | 局部先写 / 全文成文 | 直接成文 | 正文落盘 |
| **REVIEW** | 自审 | 章内自审卡（完整版） | 最小自审检查单 | 最小自审检查单 | 自审结果 |
| **WRITE_MORE** | 补搜+续写 | 下一章（→RESEARCH 补搜） | 补搜局部先写 | N/A | 同 WRITE |
| **DELIVER** | 交付 | S4→S5→S6 | S5-lite+落盘确认 | 落盘确认 | 终稿文件 |

### ESM 运行时自检协议（P0 强制，每轮对话开始时执行）

> **替代效果**：此协议统一替代散落在全文各处的 15+ 条门禁检查。模型只需执行一次自检，即可覆盖所有门禁。

> **v1.7.1 更新**：自检结论须**输出到对话**（原「心算不输出」已废弃）——外部可见才可验证，内部心算等于未执行。常规推进时可紧凑合并至状态宣告中，不占独立段落。

```
ESM 自检（每轮对话开始时执行，≤3秒；结论输出到对话）：

  Step 1：识别当前状态
    ├─ 上一轮结束时的状态标记？（从对话历史 / 状态宣告中读取）
    ├─ 磁盘上最新产出物编号？（[S0]/[S1]/[报道]/[草段]...）
    └─ 体裁等级？（A/B/C）

  Step 2：检查出口条件
    ├─ 当前状态的出口条件已满足？
    │   → 是：进入下一状态，输出状态转换宣告（含自检结论）
    └─ 否：停留在当前状态，执行必做动作

  Step 3：异常检测
    ├─ 状态-产出物不一致？（状态=WRITE 但无 Brief 文件 → 强制回退到 PLAN，不得仅「提示回退」）
    ├─ RESEARCH 状态检索 ≥15 次无文件？（→ 强制转入 PLAN + 输出研究过载预警）
    ├─ 起稿门槛 4 项自评 ≥3/4 为「是」？（→ 输出收束提醒 / 4/4 强制转入 PLAN）
    └─ 用户说「够了/先写/开始」？（→ 无条件退出 RESEARCH）

  Step 3.5：P0 事实核查（v1.8.0，WRITE/REVIEW 状态时触发）
    ├─ 当前输出/审查内容是否含「具体数字/比例/绝对化陈述/具体年份/产品版本」？
    │   → 是：核查 search-ledger.jsonl 是否有对应检索来源（yearSourceConfirmed/materialStatus）
    │       ├─ 有来源：标注「〔来源：{来源名}〕」后写入
    │       └─ 无来源：标注「〔来源：待核实〕」或先执行 WebSearch 补检再写入
    ├─ 当前正文是否出现未在 .fbs/术语锁定记录.md 中注册的近似术语？
    │   → 是：输出纠正「⚠️ 检测到近似表述「{变体}」，建议替换为已锁定「{标准}」」
    └─ S0 阶段：时间基准行是否已写入简报首行？（无则阻断进入 S1）

  Step 4：自检结论输出（每轮必须输出，可紧凑至1行）
    格式（与状态宣告合并时）：[ESM 自检] 状态:{状态} | 出口:{满足/缺:{项}} | 下一步:{动作}
    格式（独立输出时）：参见 SKILL.md「v1.7.1 执行可靠性升级」→「ESM 自检外显化」完整模板
```

### 每轮开始时的自检输出模板

```
━━ 福帮手 📍 当前进度 ━━
所在步骤：{等待开始/收集主题/调研/定结构/写稿/审稿/补搜续写/交付} · 文稿类型：{书籍/报道/短文}
下一步条件：{已满足，准备推进 / 还差：{具体缺什么}}
现在要做：{这一步第一件事}
异常：{无 / {描述问题和处理方式}}
━━━━━━━━━━━━━━━━━━━
```

**简洁模式**（和进度宣告合并时）：
`[进度] 调研中 · 还差：同类内容竞品扫描 · 下一步：搜一轮同类书/文`

> **v1.8.2 修复（P2-B）**：澄清紧凑模式边界冲突
> - **M3/A 级项目**：必须使用**完整模式** ESM 自检，禁止使用紧凑模式
> - **C 级项目**：可使用**紧凑模式** ESM 自检
> - **合并条件无效化**：「与状态切换合并时」的前提不能覆盖 M3/A 的完整模式强制要求

### 每一步的进度宣告模板（P0，状态切换时必须说出来）

> **为什么要说**：审计发现助手有时逻辑上已经在写稿了，但实际文件还没产出来。把「现在走到哪里」显式说出来，你和助手都能对齐进度，也方便事后确认哪一步出了问题。

> **更新说明**：进度宣告必须和每轮开始时的自检合并成同一次输出——说一次就够了，不要分两次输出，也不能只在脑子里想想不说出来。

```
━━━━━━ 🔄 福帮手 · 进入下一步 ━━━━━━
{上一步} → {下一步}
文稿类型：{书籍/报道/短文}
切换原因：{上一步已完成 / 你说的 / 发现问题回退}
现在要做：{这一步第一件必须做的事}
[状态确认] 条件:{满足} | 下一步:{行动}
━━━━━━━━━━━━━━━━━━━━━━
```

> **如果发现问题需要回退**：必须说出来，不能静默继续。例如：`[需要回退] 写稿 → 定结构 · 原因：章节提纲文件不存在 · 现在要做：先补一份章节提纲`

**发现异常必须说（不能静默）**：
- 准备写稿但找不到章节提纲文件 → **必须停下来回退到定结构**，不能只说「可能需要回退」
- 回退时必须说明：`[需要回退] 写稿 → 定结构 · 原因：{提纲缺失/文件对不上} · 现在要做：先出章节提纲`
- 任何异常状态都不能悄悄继续

### RESEARCH → PLAN 的「调研收束力场」

> **设计意图**：v1.6.7 的「起稿门槛」「停止调研阈值」「研究过载预警」是三条独立规则。在 ESM 框架下，它们统一为 RESEARCH 状态的出口力场——模型不需要记住三条规则，只需感知「RESEARCH 的出口条件是否已满足」。

```
RESEARCH 状态出口力场（三重递增）：

  第一重 · 自评触发器（每 3 轮检索自动触发）：
    主论点锁定？ + 一级结构确定？ + 关键事实≥2条L2？ + 已有中间文件？
    ├─ 4/4 = 【强制】退出 RESEARCH → PLAN
    ├─ 3/4 = 输出收束提醒：「当前更可能缺的是写作收束，而不是信息量。」
    └─ ≤2/4 = 继续，但须记录本轮检索目标（防无方向散搜）

  第二重 · 计数器硬阈值（累计检索 ≥15 次 && 无文件产出 && 无导语/标题/大纲）：
    → 触发研究过载预警 + 【强制】退出 RESEARCH → PLAN

  第三重 · 用户语音指令（「够了」「先写」「开始」「不搜了」）：
    → 无条件退出 RESEARCH → PLAN
```

### WRITE 状态的「产出驱动螺旋」

> **设计意图**：替代「调研→结构→写作」的瀑布假设。在 ESM 框架下，WRITE 和 RESEARCH 不再严格单向——WRITE 可通过 WRITE_MORE 回到 RESEARCH 补搜，形成螺旋式「写→发现缺口→补搜→续写」。

```
WRITE 状态内部循环（B 级体裁典型执行路径）：

  产出一个段落/节
    ├─ 证据台账有 ≥2 条 L2 级事实 → 存盘为 [草段] → 继续下一段
    ├─ 事实有缺口 → 状态切换：WRITE → WRITE_MORE
    │   └─ WRITE_MORE：针对性补搜（≤3 次，非宽搜）
    │       → 更新证据台账 → 回到 WRITE
    └─ 全部段落完成 → 合并为完整稿 → WRITE → REVIEW

  A 级体裁：WRITE_MORE = 下一章的章前检索（自然回到 RESEARCH→WRITE 循环）
  C 级体裁：无 WRITE_MORE（一次成文）
```

### ESM 体裁分流快速参照（模型执行时的「一屏速查」）

> **设计意图**：替代「在 A 级流程上做减法」的思维方式。模型不需要知道 A 级有什么然后想 B 级跳过什么——只需查本表，按体裁直接执行对应列。

| 维度 | A 级（书/手册/白皮书） | B 级（报道/专题/特稿） | C 级（短评/快讯） |
|------|----------------------|----------------------|-------------------|
| **INTAKE 必做** | 主题+读者+体裁+体量 | 主题+读者+体裁（一轮） | 主题确认 |
| **RESEARCH 必做** | S0三项+S0-E素材+作者元知识 | S0-lite+时间戳+1轮竞品 | ≥1次检索 |
| **PLAN 必做** | S1→S2→S2.5→Brief粒度协商 | 证据台账→MVD→Report Brief | 跳过（直接写） |
| **WRITE 模式** | Chapter Brief→逐章成文 | 局部先写→合并→统稿 | 一次成文 |
| **REVIEW 标准** | 章内自审卡（完整，5层） | 最小自审检查单（3层） | 最小自审检查单 |
| **DELIVER 必做** | S4构建→S5终审→S6交付 | S5-lite+落盘确认 | 落盘确认 |
| **WRITE_MORE 触发** | 下一章 | 段落事实缺口 | N/A |
| **起稿门槛** | S2→S3门禁（已有） | 证据充足/时间线就绪/结构可写/样段可产（任一） | 无 |
| **最低检索深度** | 关键事实L2 / 精确数字L3 | 关键事实L2 | L1 |
| **强制落盘阈值** | 所有章节 | ≥2000字 | ≥2000字 |

### ESM 与原有规则的关系

ESM **不替代**下文的详细规则（检索六大场景、Chapter Brief 模板、证据台账、MVD 等），而是为它们提供**执行调度层**：

| 作用 | ESM 做什么 | 下文详细规则做什么 |
|------|-----------|-------------------|
| **何时** | 告诉模型「现在该执行哪组规则」 | 被 ESM 调度后，提供「怎么执行」的细节 |
| **状态感知** | 「我在 RESEARCH，出口未满足」 | 「RESEARCH 下须执行检索六大场景」 |
| **异常检测** | 「状态=WRITE 但 Brief 不存在 → 回退」 | Brief 模板的具体内容 |
| **体裁分流** | 「当前 B 级，PLAN 出口=MVD+Report Brief」 | MVD / Report Brief 的具体格式 |
| **螺旋推进** | 「WRITE→WRITE_MORE→WRITE」循环 | 局部先写的触发条件与段落命名 |

### 最容易遗漏的 11 项（P0/P1）

1. **（v1.7.0 新增）** B/C 级体裁未查 ESM 体裁分流表，在 A 级流程上做减法导致门禁失效。
2. **（v1.7.0 新增）** 状态切换时未输出宣告，用户不知道「我们现在在哪」。
3. **（v1.7.1 新增）** ESM 自检仅心算未输出对话——等同于未执行，无法被审计验证。
4. **（v1.7.1 新增）** S0 调研只做产业研究，漏掉内容竞品（同类书/文）和读者分析。
5. S0 第一个动作没有做时间戳检索；或检索 query 中硬编码了具体年份（2024/2025 等）。
6. 检索做了但 `search-ledger.jsonl` 为空；或每轮检索结束后未输出自评结论。
7. Chapter Brief 输出了但没存盘。
8. 100 万字项目未在 S0 早期宣告 M3。

## §3.0.5 强制联网检索（写作质量门禁）

> **原则**：凡涉及事实、数据、政策、竞品、工具能力、行业结论的表述，必须先检索再写入；禁止凭模型记忆直接落稿。配置与阶段清单见 [`../05-ops/search-policy.json`](../05-ops/search-policy.json)。

| 阶段 | 强制动作 | 说明 |
|------|----------|------|
| **S0** | 竞品/读者/市场类查询均须执行检索 | **宿主**侧用 WebSearch/WebFetch 完成；`search-policy.json` 中 `s0ParallelQueries` 为建议轮次 |
| **S1** | 定调前检索主题与受众相关公开讨论/定义 | 用于校准「核心主张」与差异化 |
| **S2** | 目录设计前检索同类书目结构与空白点 | 至少 1 轮结构化检索 |
| **S2.5** | 脉络与**本书变现**路径须有检索支撑；**市场/行业**信息仅作交叉验证的背景论据 | 与 S0 数据交叉验证，避免用赛道叙事顶替本稿变现 |
| **S3 每章** | **每章成文前 ≥2 次**主题相关检索（默认） | 次数以 `search-policy.json` 的 `chapterWriting.minQueriesPerChapter` 为准；宿主应记录检索次数以便审计 |
| **S5** | 终稿事实与数据与「数据保鲜表」对齐前的抽查检索 | 对高风险句逐条验证 |

### 「禁止无检索落稿」单一禁令（与 SKILL / policy 对齐）

以下仅为**同一禁令**在不同文件中的互补表述，执行时**取严**，勿因措辞差异降低标准：

| 来源 | 作用 |
|------|------|
| [`SKILL.md`](../../SKILL.md) §0 **联网搜索规范** | 主规范叙事与用户可见承诺 |
| 本节 §3.0.5 上表 | 按阶段的操作化清单 |
| [`search-policy.json`](../05-ops/search-policy.json) | 机读阶段列表与每章最少检索次数 |
| **本文 [§3.0.6](#306-联网搜索增强规范六大场景)** | **时间戳 / 年份标签 / 自增强 / 疑难补检 / 优质源六大增强场景（P0/P1 分级）** |

**禁令核心**：凡应核验的事实型/数据型/政策竞品型内容，**须先 WebSearch/WebFetch（或宿主等价工具）再落稿**；禁止仅用模型内省充当「已查证」。用户声明纯虚构并自担风险时，须在对话与产出物中**可见标注**。

**宿主**侧：用自然语言要求并行成员先输出「检索 query 列表 + 结果摘要」再动笔；本技能包**不含自研后端**，门禁由宿主按本规范落实。

### §3.0.5-降级协议：联网不可用时的强制可见声明（P0 强制，v1.9.0 新增）

> **来源**：2026-04-02 杜氏项目复盘 P0-3——全书 23 章无任何联网检索，全程静默降级为纯内省写作，用户完全无感知。  
> **适用场景**：章前检索门禁触发时（S3 每章开始前），若检测到 WebSearch/WebFetch 工具不可用。

**执行规则（P0 强制，优先级等同于联网门禁本身）**：

```
§3.0.5-降级协议执行流程：

Step 1：在每轮写作开始前（或每章章前检索开始时），执行联网可用性探测：
  尝试调用 WebSearch，query 为「{书名} 最新」或「今天日期」

Step 2：若探测成功 → 继续正常执行章前检索门禁

Step 3：若探测失败（工具不可用）→ 立即在对话中告知，不能悄悄继续：

  「⚠️ 联网查不了
  
    按照本书的写作规范，每章需要联网核实 ≥N 次
    （族谱/历史/学术类需要 ≥3 次）。
    现在联网工具不可用，没办法满足这个要求。
    
    你来决定怎么走：
    A. 等联网好了再继续
    B. 用"内省模式"写：继续写，但每章文件头部会加上
       [⚠️ 内省稿·未联网核实·数据类内容仅供参考]
    C. 先只出章节骨架，不写正文内容」

Step 4：在用户明确选择前，禁止开始正文写作。

Step 5：用户选 B 时，每章文件头部须包含：
  > ⚠️ 本章为内省稿，未经联网检索核查。数据类内容（人口、分布、
  > 年份、人名等）均来自模型训练记忆，建议出版前逐条核实。
```

**本协议不受用户"无需确认/持续执行"等授权语影响**（见 `SKILL.md` §v1.9.0 升级1 禁令A）。

## §3.0.6 联网搜索增强规范（六大场景）

> **定位**：本节是 §3.0.5「强制联网检索」的执行增强层，专项约束六类高风险场景；与 [`search-policy.json`](../05-ops/search-policy.json) 中 `temporalAccuracy` / `searchEnhancement` 字段机读配置对齐，**取严**执行。

### 场景一：时间戳获取（P0 强制）

**问题**：模型内置知识有训练截止日期，若不检索当前日期，会错误地将「本次写作时间」锁定在过时时间点。

**规范**：

```
S0 第一个动作 → WebSearch 查询当前日期（query 示例：「今天日期」「今天是哪年哪月哪日」）
→ 将结果写入 [S0] 调研简报首部「时间基准：YYYY年MM月DD日（来源：WebSearch）」
→ 后续所有阶段引用日期以此为准，禁止使用模型内置推断值
```

- 若 WebSearch 返回不确定结果，须再次检索或向用户确认，**不得**以模型估算值替代。
- `search-policy.json` 字段：`temporalAccuracy.requireTimestampSearchAtS0: true`

---

### 场景二：禁止无检索年份标签（P0 强制）

**问题**：模型倾向在未检索的情况下自动写入「2023年」「2024年」「近年来」等，误导读者误信过时数据。

**规范**：

| 情形 | 规则 |
|------|------|
| 正文中写具体年份（如「2024年某政策出台」） | 须先 WebSearch 取来源再写入；来源在「检索执行记录」可追溯 |
| 正文中写「近年来」「当前」「最新」 | 须先检索验证该表述的时效性，或明确标注「截至[检索日期]」 |
| 模型无法检索但主观认为「应该是 202X 年」 | 须标注「（待核实年份）」，禁止伪装成已确认事实写入正文 |
| 用户书面声明接受未核实年份并自担风险 | 在产出物中可见标注「（年份未经检索核实）」 |

- `search-policy.json` 字段：`temporalAccuracy.forbidBareYearWithoutSource: true`、`temporalAccuracy.yearLabelPolicy: "search_before_write"`

---

### 场景三：最新知识获取（每章强制）

**问题**：凭模型记忆写作的章节，极易引用已被更新或推翻的数据/方法/政策。

**规范**：

- S3 每章成文前 ≥2 次检索中，**至少 1 次**的 query 须含时效性限定词：「最新」「近三年」「2024年」「最近发布」等（见 `search-policy.json` → `searchEnhancement.freshKeywordInjection`）。
- 章前检索结论须嵌入正文或「本章数据来源索引」；凡含具体数字/比例/政策条文的句子，须有可追溯来源（与 §3.0.5 「禁令核心」一致）。
- S5 终审时，对「高时效性」句（含明确年份或「最新」「当前」等词）逐条抽查，验证来源是否仍有效。

---

### 场景四：自增强搜索策略（建议执行，P1）

**问题**：每章用相同 query 检索，搜索质量不会提升；检索到高质量专题页应触发策略迭代。

**规范**：

```
本轮检索结束后 → 评估结果信息密度与来源权威性
→ 若发现新专题词 / 权威来源子域 / 意外高相关页面
→ 生成优化 query（基于新词变形），用于后续章节
→ 在 .fbs/search-ledger.jsonl 中记录（kind=search，含 queryOptimization 字段）
→ 后续同类章节优先使用迭代后的高效 query
```

- 有效 query 变形（新词/更精确的限定词）应记录；无效 query 原因（结果质量差、来源过时）也应记录，避免重复低效检索。
- `search-policy.json` 字段：`searchEnhancement.selfImprovingStrategy`

---

### 场景五：疑难问题自动搜索学习（P0 强制）

**问题**：模型在内心评估置信度低的情况下，仍用模糊词掩盖未经验证的事实写入正文。

**触发条件**：模型生成过程中，对某事实句的内部置信度 < 0.8，**或**措辞中出现以下词语：

> 不确定、可能、大约、据说、印象中、记忆中、似乎、应该是、好像是

**规范**：

```
检测到低置信度事实句 → 暂停正文写入
→ 触发 WebSearch 补充检索（query = 该事实的核心主张）
→ 检索成功 → 更新事实句，标注来源，继续写入
→ 检索失败 → 标注「（数据待核实，来源：[检索失败]）」+ 章末记录
→ 禁止静默写入推测值 / 禁止用「数据待补充」占位后忘记补齐
```

- `search-policy.json` 字段：`searchEnhancement.autoSearchOnUncertainty`

---

### 场景六：发现并记录优质搜索源（P1 建议）

**问题**：每次从零开始检索，忽视了本书主题下已发现的高质量专项信息源。

**规范**：

1. **S0 后汇总**：检索完成后，在 `[S0] 调研简报` 末附「本书推荐信息源」表（至少 3 条）：

   | 来源名称 | URL | 擅长领域 | 质量等级（1–5）|
   |---------|-----|---------|--------------|

2. **持续追加**：S3 成文过程中发现高质量新源（质量等级 ≥4）时，追加写入 `.fbs/high-quality-domains.json`；后续章节检索优先向该表域名发起 WebFetch。

3. **来源质量存疑**：遇到「无日期个人博客」「内容农场聚合站」「二手转载无原始链接」等低质来源，须向用户说明并确认是否采信，不得默认引用。

4. **`search-policy.json` 字段**：`searchEnhancement.sourceQualityTracking`、`searchEnhancement.searchSourceDiscovery`

---

### 六大场景汇总速查

| 场景 | 级别 | 触发时机 | 失败后处置 |
|------|------|---------|-----------|
| 时间戳获取 | **P0** | S0 第一步 | 再次检索或用户确认，禁止估算 |
| 禁止无源年份标签 | **P0** | 写入含年份句时 | 标注「（待核实年份）」 |
| 最新知识获取 | **P0** | S3 每章章前检索 | query 须含时效词；S5 抽查高时效句 |
| 自增强搜索策略 | **P1** | 每轮检索结束后 | 记录 ledger，无强制阻断 |
| 疑难自动搜索学习 | **P0** | 低置信度事实句 | 标注待核实，章末记录，禁止静默 |
| 优质源发现记录 | **P1** | S0 汇总 + S3 追加 | 可延迟，但 S0 简报须含≥3条 |

## §3.0.7 检索与 ledger 登记原子绑定（P0 强制，v1.6.5 新增）

> **根因**：审计发现模型实际执行了多次联网检索，但 `search-ledger.jsonl` 为空——检索已做但未记账。原因是 ledger 登记在规范中属「应做」但执行中无检查点。

### 原子性约束

每次调用 WebSearch / WebFetch 后，**同一轮工具调用中**（或紧接下一轮）必须追加一行到 `.fbs/search-ledger.jsonl`（若 `.fbs/` 已初始化）或在对话中输出等价登记记录（若 `.fbs/` 未初始化），包含：

```jsonl
{"timestamp":"ISO","query":"…","url":"…","ok":true,"resultSummary":"≤100字摘要","chapterId":"S0/ChNN/report","depthLevel":"L1/L2/L3"}
```

### 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| `timestamp` | ✅ | ISO 格式时间戳 |
| `query` | ✅ | 检索使用的查询词 |
| `url` | ✅ | 检索目标 URL（搜索引擎结果页或具体页面） |
| `ok` | ✅ | 是否成功获取有效结果 |
| `resultSummary` | ✅ | ≤100 字的结果摘要 |
| `chapterId` | ✅ | 所属阶段/章节（如 `S0`、`Ch01`、`report`） |
| `depthLevel` | ✅ | 检索深度等级：`L1`（搜索摘要）/ `L2`（页面正文）/ `L3`（交叉验证） |

> **兼容说明（v1.7.0 修订）**：历史账本可读取别名字段 `ts`→`timestamp`、`summary`→`resultSummary`、`chapter`→`chapterId`、`depth`→`depthLevel`；新写入与新规范一律使用标准字段名。离线校验可执行：`node scripts/enforce-search-policy.mjs --skill-root <技能根> --book-root <本书根> --chapter-id <id> --verify-atomicity`。

### 违反判定

- 若 `search-ledger.jsonl` 最后一条的 `timestamp` 早于最近一次 WebSearch/WebFetch 的调用时间，视为「检索已做但未记账」
- **A 级体裁**：S3 正文门禁不通过，须补登记后方可继续
- **B 级体裁**：成文门禁不通过，须补登记后方可继续
- **C 级体裁**：成文后最小自审中核查

### B/C 级体裁的简化处理

- 若 `.fbs/` 未初始化（B/C 级体裁可能不初始化完整工件），检索登记须在**对话中以结构化格式可见输出**，作为等价登记
- 对话中登记格式：`📝 检索登记：[query] → [L1/L2/L3] → [ok/fail] → [≤50字摘要]`

## §3.0.8 检索深度分级（P1 建议，v1.6.5 新增）

> **根因**：审计发现模型的联网检索全部停留在搜索引擎结果页的摘要聚合（L1），而非直接访问一手来源页面（L2）。搜索引擎摘要 ≠ 一手来源，但规范未区分二者的可信度等级，导致「v1.0 公告发布」等关键事实的来源仅为 Bing 搜索摘要而非官网原文。

### 三级检索深度

| 深度等级 | 定义 | 可信度 | 适用场景 | 工具对应 |
|---------|------|--------|---------|---------|
| **L1 摘要级** | 搜索引擎结果页的标题+摘要 | 中（可用于背景概述、趋势判断） | 快速扫描、信源发现、宏观叙事 | WebSearch |
| **L2 页面级** | WebFetch 直接访问目标页面获取正文 | 高（可用于事实引用、精确数据） | 关键事实核实、日期确认、功能描述 | WebFetch |
| **L3 交叉级** | ≥2 个独立来源的 L2 相互印证 | 最高 | 争议性事实、精确数字、政策条文 | 多次 WebFetch |

### 体裁与最低检索深度要求

| 体裁等级 | 关键事实最低深度 | 精确数字最低深度 | 背景叙事最低深度 |
|---------|----------------|----------------|----------------|
| **A 级（书/手册/白皮书）** | L2 | **L3** | L1 |
| **B 级（报道/专题/特稿）** | **L2** | L2 | L1 |
| **C 级（短评/快讯）** | L1 | L1 | L1 |

### 深度升级触发条件

```
检索结果评估（每次 WebSearch 完成后）：
  ├─ 结果涉及关键事实（日期/版本号/功能/人名/机构名）
  │   且当前深度 = L1
  │   → 触发深度升级：对该信源执行 WebFetch 获取 L2
  ├─ 结果涉及精确数字（百分比/金额/数量/排名）
  │   且 A 级体裁
  │   → 触发深度升级：需 L3（≥2 个独立 L2 来源交叉验证）
  └─ 结果仅为背景/趋势/定性判断
      → L1 即可，无需升级
```

### 深度等级标注

- `search-ledger.jsonl` 中的 `depthLevel` 字段须如实标注
- Report Brief / Chapter Brief 中的「信源状态」须按深度等级分类汇报
- 正文中引用 L1 级来源的事实，须在来源标注中注明「来源：搜索引擎摘要」以区分

## §3.0.55 阶段顺序与禁止跨阶段

> **目的**：避免未确认的定位/目录被后续成文「锁死」，或终稿流程倒序执行导致审计失效。

| 规则 | 说明 |
|------|------|
| **顺序** | 默认严格按 **S0（可跳过，见下）→ S1 → S2 → S2.5 → S3 → S4 → S5 → S6**；前一阶段用户确认或明确放行后，再进入下一阶段。 |
| **禁止跨阶段** | 不得在 **未交付/未确认** S1 定位稿的情况下进入 S2 目录定稿；不得在 **未确认** S2.5 脉络的情况下批量启动 S3 全书写入；不得跳过 S5 终审直接对外宣称「定稿发布」（除非用户书面确认接受预览版并自担风险）。 |
| **例外** | 用户明确要求「只改第 N 章」时，允许在已存在经确认的全书骨架下**局部回退 S3**，但仍须遵守该章的 **章前检索门禁**（`search-policy.json`）。 |
| **审计** | 宿主应记录「当前阶段 ID + 最近确认时间」，供质量报告。 |

## §3.0 隐式确认最低确认清单

> **目的**：规范用户确认行为，避免"过少致失控感、过多致中断感"  
> **设计原则**：审批点设在"方向性决策"节点，非"执行细节"节点

### A层：自动确认（极低风险，无需确认）

| 场景 | 示例 | 处理方式 |
|------|------|----------|
| 错别字修正 | 的/地/得错误 | 自动修正 |
| 标点规范化 | 引号/省略号全角半角 | 自动规范化 |
| 格式统一 | 标题层级对齐模板 | 自动对齐 |
| 数据保鲜标注 | 来源URL补全 | 自动补全 |

### B层：隐性确认（必做，用户无感知打断）

| 节点 | 确认项 | 展示方式 |
|------|--------|----------|
| **S1-C 定位确认** | 主题 + 读者 + 风格 + 篇幅 + 大纲 | 定位确认卡（一屏展示5项） |
| **S2.5 脉络确认** | 内容方向 + 变现路径建议 | 脉络摘要卡 |
| **S3 大纲审批** | 章节结构 + 核心论点 | 结构预览图；**进入 S3 成文前须显性确认**（见阶段2「S2→S3 硬性门禁」） |
| **S5 终稿预览** | 全文质量报告 + 评分卡 | 评分详情卡 |

### H2 极简协同规范（人类绩效优化，AI菜单·人选套餐）

> **来源**：人机协同洞察55-58——「1字选择杠杆率1:600；追问效率是长提示词25倍；让AI设计菜单，人只管点选」。  
> **目的**：减少用户在每个阶段的认知负担，最大化人类「方向确认」价值，最小化「重复描述」成本。

**执行原则**：

| 原则 | 说明 |
|------|------|
| **AI先出菜单** | 每个决策节点，AI必须先呈现2-3个具体选项（含推荐项标注★），用户只需回复序号或「都要」，无需重新描述需求 |
| **贪婪策略默认** | 选项中若含「全部执行」选项，默认标注为「推荐」；AI不应暗示「选哪个都行，随便」——应给出清晰推荐理由 |
| **追问优于长提示** | 用户只说「继续」「下一步」时，AI应主动提供选项菜单，而非让用户重新说明需求 |
| **批量确认节点** | S2 目录定稿后，用「全章覆盖确认卡」一次性让用户确认各章的主题/字数/素材状态，而非逐章询问 |

**阶段菜单模板（执行示例）**：

```markdown
S3 章节完成后的标准菜单：
━━━━━━━━━━━━━━━━━━━━
✅ 第N章已完成，质量评分：{折算分}/10
━━━━━━━━━━━━━━━━━━━━
下一步选择：
A. ★ 继续第N+1章（推荐，保持节奏）
B. 先审阅本章，我来提修改意见
C. 暂停，更新素材库后继续
D. 查看本章自审卡详情
━━━━━━━━━━━━━━━━━━━━
回复 A/B/C/D 或直接说「继续」（默认A）
```

### C层：显性确认（必做，阻断执行）

| 场景 | 阻断条件 | 确认方式 |
|------|----------|----------|
| **删除章节** | 任何删除操作 | 弹窗确认，显示影响范围 |

### 长文产出强制落盘（P0 强制，与体裁无关，v1.6.5 新增）

> **根因**：审计发现模型将 B/C 级体裁任务理解为「对话式一次性生成」，未触发 `write_to_file`，导致数千字产出物仅存在于对话流中，用户离开会话即丢失。

**规则**：凡对话中单次输出超过 **2000 字**的内容（正文/报道/章节/专题），**必须**在输出完成后调用 `write_to_file` 存盘。

```
产出物字数统计（成文完成后）：
  ├─ ≥2000 字 → 【强制】调用 write_to_file 存盘
  │   文件路径：{workspace}/{产出物编号或体裁标签}-{标题}.md
  │   A 级体裁：{workspace}/[S3-ChNN] 第N章-标题.md（与原规范一致）
  │   B 级体裁：{workspace}/[报道] {标题}.md 或 [专题] {标题}.md
  │   C 级体裁：{workspace}/[短评] {标题}.md
  │   存盘后输出确认：✅ 已存盘至 {文件路径}
  └─ <2000 字 → 建议存盘，非强制
```

**不落盘 = 不完成**：在声明「已完成写作」之前，须确认产出物已落盘。若对话中未调用 `write_to_file` 而宣称完成，视为流程违规。

**与 §3.X 的关系**：本规则是 §3.X 强制保存检查点的**泛化扩展**——§3.X 仅约束 A 级体裁的阶段产出物，本规则将落盘义务扩展到所有体裁的所有长文产出。

### §3.X.1 关键策划文件保存验证（P0 强制，v1.9.0 新增）

> **来源**：2026-04-02 杜氏项目复盘 P1-5——`[S2.5]脉络确认稿.md` 的 `write_to_file` 工具调用成功，但 `list_dir` 未显示该文件，模型以「工具调用成功」即等同「文件已保存」，未执行验证，后续流程基于不存在的文件继续执行。  
> **根因**：宿主环境偶发 UI 报错与磁盘真值不同步，工具调用返回成功不等于文件确实持久化。

**执行规则（P0 强制）**：

```
关键策划文件写入后，必须执行读回验证：

适用文件清单（以下文件写入后须验证，不限于此）：
  - [S0] 调研简报.md
  - [S1] 定位确认稿.md
  - [S2] 目录草案.md
  - [S2.5] 脉络确认稿.md
  - .fbs/chapter-status.md（初始化或重建后）
  - .fbs/book-context-brief.md
  - .fbs/author-meta.md
  - .fbs/project-config.json

验证流程（每次写入关键策划文件后执行）：

Step 1：调用 write_to_file 写入文件

Step 2：立即调用 read_file 读回该文件的前 20 行

Step 3：验证读回内容与写入内容一致（至少验证标题行 + 前3行实质内容）：
  ├─ 一致 → 输出 ✅ {文件名} 已验证写入
  └─ 不一致或读取失败 → 输出：
     「⚠️ [写入验证失败] {文件名} 写入结果与预期不一致。
      将重试写入（最多3次）。」
     → 重试，每次间隔约3秒
     → 3次仍失败 → 输出完整内容到对话，提示用户手动保存

禁止：
  ❌ 以「工具调用成功/返回 success」替代 read_file 验证
  ❌ 仅凭对话历史中的「已写入」声明确认文件存在
  ❌ 跳过验证直接进入下一阶段，后续基于不存在的文件执行
```

**验证输出格式**：
```
✅ [写入验证] [S2.5] 脉络确认稿.md | 已确认写入 | 前3行：{内容摘要}
```

**与 §3.X 强制保存检查点的关系**：
- §3.X 强制保存：约束「何时必须写」
- 本节 §3.X.1 验证：约束「写了之后必须确认真的写成功了」
- 两者结合构成完整的落盘可靠性保障

### S0-A 竞品扫描（内容替代物优先）

- 搜索维度（默认）：国内若干 + 海外若干 **同类出版物或等效长内容**（书名/报告标题/头部文章/课程大纲级竞品）
- 搜索语言：中文 + 英文（必要时日文/韩文）
- 输出：**内容竞品对照表**（定位、篇幅、渠道、差异点、空白位）+ 差异化机会；若存在产品横评体裁，**另表**「产品参照（非默认竞品）」

### S0 检索失败降级协议（P0）

> 搜索端点异常时不得静默继续。须按 `search-policy.json` 的有效端点与失败处理执行。

**降级路径（执行顺序，禁止跳步）**：

```
S0 任一轮检索失败时：
Step 1 → 判断失败类型
  ├─ 响应含 '<!DOCTYPE html>' 且不含 '<item>' → JS渲染空壳 → 切换 RSS 端点重试一次
  ├─ 超时（>15s）→ 记录 ok=false reason=timeout → 进入 Step 2
  └─ 网络不可达 → 记录 ok=false reason=network_unreachable → 进入 Step 2

Step 2 → 记录到 .fbs/search-ledger.jsonl（kind=search, ok=false, reason=…）

Step 3 → 向用户可见告知（禁止静默继续）：
  「⚠️ S0 检索失败（{失败轮次}/{总轮次}）：原因 {reason}。
   本轮调研简报对应部分将标注来源为「模型知识，未经外部检索核实」。
   如需重试，请回复「重新检索」；如继续，请回复「知道了，继续」。」

Step 4 → 用模型知识兜底，但须在简报中醒目标注：
  - 调研简报标题降级：「S0 调研简报（⚠️ 检索部分失败，{N}/{M}条来自模型知识）」
  - 每条未经检索的结论段末标注：〔模型知识，未经外部检索核实〕
  - 简报末尾增加「检索执行情况」摘要表

Step 5 → 全部检索均失败时（ok=false 条数 = 总计划条数），须额外输出警告：
  「🔴 本次 S0 调研全部检索失败，简报内容 100% 来自模型训练知识。
   建议：① 检查网络连通性；② 重试 RSS 端点；③ 继续写作须知情接受「未核实」风险。」
  并在 .fbs/project-config.json 写入 "s0SearchStatus": "all-failed-model-knowledge-only"
```

**禁止行为**：
- 禁止将检索失败包装为「调研已完成」而不给任何提示
- 禁止在检索失败后不标注直接使用模型知识写入简报结论
- 禁止以「已做了一些调研」模糊表述掩盖 0 字节有效检索的事实

#### 起稿门槛与停止调研阈值（P0 强制，v1.6.7 新增）

> **根因**：WorkBuddy 审计发现模型检索强度极高（9 次公开搜索 + 12 次页面抓取 + 8 次本地检索），但始终未进入正文写作。流程缺少显式的「够了，先写」触发条件，导致调研惯性压住写作推进——材料越来越多、判断迟迟不锁、起稿被研究拖死。

##### B 级体裁起稿门槛（满足任一组即 **必须** 停止新增宽搜、进入起稿）

| 门槛组 | 条件 | 说明 |
|--------|------|------|
| **证据充足** | ≥10 条一手来源（L2+）已登记到 search-ledger | 一手来源指 WebFetch 直接获取的官方/仓库/数据页面 |

| **样段可产** | 能写出 300 字导语 + 800 字主体样段 | 主观判断，但须在 Report Brief 前自评 |

```

  ├─ 检查：一级结构是否已确定？       → 是/否

### S2 规划定位：活骨架，不是合同

> S2 规划会随检索与认知更新而变化，因此应支持可追踪修订。

**S2 规划的正确定位**：S2 规划是「活的骨架」，不是「一次性锁死的合同」。允许在 S3 写作过程中对 S2 规划进行局部修订。

**规划修订规则**：

| 场景 | 处理方式 |
|------|----------|
| S3 写某章时，发现 S2 规划的小节主题与检索结果不符 | 可修订该章 S2 规划（更新 MD 文件），在 `chapter-status.md` 对应行备注「S2已修订·{原因}·{修订时间}」 |

| 用户主动要求修改目录 | 正常流程，无需额外说明；大幅修改（≥5章）须触发结构仲裁核查 |
| 保持不变 | 无需记录 |

**在每章 Chapter Brief 的「上下文衔接」字段增加**：`S2规划状态：{最新（未修订）/ 已修订（见chapter-status.md）}`，让成文者在每章开始前知悉骨架是否已更新。

> **M3 宣告时序（P0 强制，v1.8.1 修复）**：若用户在 **S0 启动时已明确说明字数 ≥100万字**（如「写一部100万字的…」），须在 **S0 规模判定的同一轮**即完成 M3 宣告并立即加载 `large-scale-book-strategy.md`，输出：「本书字数 ≥100万字，自动升级为 **M3 巨型项目**，已启用分卷写作、开机四步协议、结构仲裁日志。」**禁止** 先做完 S0→S1→S2 全流程、等到 S3 进入条件检查才宣告 M3 等级（此时最关键的 M3 增强步骤——S0-E 素材需求清单 P0 强制——已错过执行时机）。**时序约定**：规模识别 → 立即宣告 → 立即加载策略 → 再执行对应规模的 S0-E/检索策略增强。

### S3 启动与章前检索：防卡顿（体验强约束）

> **现象**：用户确认大纲后，界面长时间无新消息，误以为「卡住」——常见于 **章前检索串行**（每 query 可达策略超时，默认约 15s 量级）、**模型首轮批量 Read 多份长规范**、或 **工具执行中无可见状态**。另有一类：宿主/平台返回 **`too many requests`（如 WorkBuddy Error Code 14003）**，属平台级请求限流，须按退避规程处理（见下表）。

| 根因 | 对用户侧建议（模型/宿主须落实） |
|------|--------------------------------|
| 章前 ≥N 次检索依次执行 | **首条可见回复**须明示：已进入 **S3**、本章标题/编号、将先做 **章前检索 N 次**（N 以 `search-policy.json` 为准），再进入成稿；不得静默开检。 |
| 单次检索等待 | 预计本段章前检索 **≥30s** 或已连续静默 **>30s** 时，须按 `SKILL.md` §0 **每 15s** 一行可读进度（例如「章前检索 1/2…」）；与「单轮 `webSearch` 默认约 15s 机读超时」并存——**15s 心跳**是**对话可见性**，**15s 超时**是**单次调用熔断**，勿混为一谈。宿主 UI 宜展示工具进行中。 |
| **平台限流（14003 / too many requests）** | **立即停止当前并发检索**；向用户说明「平台限流，等待 N 秒后重试」（N = `rateLimitGuard.backoffOnRateLimitMs`，默认 10s）；退避期满后 **串行** 补齐剩余查询；仍失败超过 `maxRetriesOnRateLimit`（默认 2 次）则记录为 `ok=false reason=rate_limit` 并跳过；禁止静默卡死或无限重试。**根本原因**：S0/S3 并发 WebSearch 过多，已触碰平台 QPS 上限；缓解方式见下方「降并发操作建议」。 |
| 规范冷读 | **在输出本章任何成稿段落之前**，避免无说明地并行 **Read 超过 3 份长文档**；优先走 [`skill-index.md`](./skill-index.md) 的短路径或会话已加载的节选。 |
| 检索失败/超时 | **立即**一句话说明原因与可重试项，禁止长时间空白后突然输出正文。 |

#### 遭遇 14003 / too many requests 时的降并发操作建议

> 适用于 **WorkBuddy** 及其他可能有 QPS 限制的宿主环境。

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | **立刻停止当前轮并发** | 不再同时发出多条 WebSearch；把未发出的查询排队 |
| 2 | **等待退避时间** | 默认 10s（`rateLimitGuard.backoffOnRateLimitMs`）；可在对话中倒计时告知用户 |
| 3 | **改串行逐条重发** | 每条完成后间隔 ≥3s（`minIntervalBetweenQueriesMs`）再发下一条 |
| 4 | **超限则跳过并标记** | 超过 `maxRetriesOnRateLimit`（默认 2）次仍报限流，跳过该查询，写入 `rate_limit` 标记，继续后续章节 |
| 5 | **告知用户** | 明确说明「本章检索 X/N 条成功，Y 条因平台限流跳过，后续人工补检索」；禁止静默伪造已查证 |
| 6 | **长期缓解** | 检查 `search-policy.json` → `searchAccessPolicy.s0MaxConcurrentQueries`（默认已调低至 2）；S0 阶段可向用户确认是否跳过部分检索轮次，减少单会话内总请求数 |

**集成侧（可选）**：使用 `BookWorkflowOrchestrator.execute({ mode: 'chapter_gate', …, onProgress })` 或 `chapter_pipeline` 时，章前门禁会对 **每次检索** 触发进度事件（见 `SearchBundle.executeChapterGate` / `MultiAgentPipeline`），宿主应将 `nextAction`、`gateQueryIndex` 等映射为可见文案，降低卡顿感。`rateLimitGuard` 参数可由宿主侧覆盖注入。

#### S3 成文卡顿 → 手动停止 → 重发「继续」→ 14003：专项中断恢复规程

> **现象**：S3 章节**成文阶段**（非检索阶段）长时间无新输出 → 用户手动停止任务 → **立即**重新发送「继续」请求 → WorkBuddy 返回 `too many requests (Error Code: 14003)`。  
> **根因**：前一个任务被强制中断后，平台需要时间释放并发任务槽或 token 速率计数；立即重发触碰了平台级并发或速率上限，与检索 QPS 无关。

**一、预防：模型侧成文心跳（最优先）**

| 要求 | 说明 |
|------|------|
| **成文期间 ≤15s 输出一行可见进度** | 即使模型正在组织长段落，也须每 ≤15s 输出一行占位进度（如「正在起草第2章第3节…」），让用户知晓系统未卡死，避免误判后手动停止。此要求与章前检索心跳共用同一 ≤15s 规则，**成文阶段同样适用**。 |
| **分块输出，不做长段批量缓冲** | 每完成一个小节（`###` 级或约300–500字）即推送输出，不等全章写完再一次性输出；减少平台侧单次 token 流量峰值。 |

**二、已停止后：冷却等待（强建议）**

手动停止任务后，**建议等待 15–30 秒**再重新发送请求，让平台充分释放前一个任务占用的资源。等待期间可检查本书根磁盘文件，确认已落盘的进度（见下）。

**三、重发「继续」的正确话术与磁盘真值优先**

| 场景 | 推荐话术 | 说明 |
|------|----------|------|
| 成文中途停止，已有部分落盘 | 「继续写第 N 章，从『[上次停止处的小节标题]』之后接着写」 | 模型须先 Read 磁盘确认已落盘内容，从**断点**续写，**禁止**重新生成已落盘段落 |
| 停止较早，落盘内容少或不确定 | 「重新写第 N 章」或「从第 N 章第1节开始」 | 明确指定起点，避免模型从全书 S0 重新触发 |
| 不确定停到哪里 | 先说「列出当前已完成的章节文件」，确认后再续写 | 利用磁盘扫描（`sync-book-chapter-index.mjs`）核对进度 |

**禁止事项（模型侧）**：
- 收到「继续」后，禁止不读磁盘直接重写已落盘章节
- 禁止在冷却期内循环发送多条请求（加剧限流）
- 禁止将「成文卡顿」误归因为「检索问题」而重跑 S0 全量检索

**四、冷却等待期仍遇 14003 的升级处理**

| 等待时长 | 处置 |
|----------|------|
| 已等 30s，仍 14003 | 再等 30–60s 后重发；可向用户说明「平台资源释放中，稍后重试」 |
| 多次重发均失败 | 建议用户刷新 WorkBuddy 页面（或开新会话）后，指定章节从断点续写 |
| 新会话续写时 | 告知模型「本书根路径」与「已完成章节列表」，模型须先扫描磁盘再决定写哪章 |

#### S3 全自动运行（无人值守）：Auto-Run Unit 规程

> **适用场景**：用户授权模型在无人值守情况下连续成文（如「帮我把第一编全部写完」）。  
> **核心原则**：全自动 ≠ 永不停止。正确设计是**以「编（Part）」为单元执行，完成后主动停止报告**。

**一、执行前：会话开机确认（强制）**

启动全自动前，须先完成 M2 开机四步（见 `large-scale-book-strategy.md §4.1`），包括：
1. 读取并确认 `.fbs/book-context-brief.md` 台账新鲜度
2. 读取并确认 `.fbs/chapter-status.md` 已完成状态（`restoreStateFromDisk` 语义）
3. 检查 `.fbs/rate-budget.json` 限流预算（rateLimitRate > 0.3 须告警）
4. 检查是否存在 `emergency-draft-*.md`（存在则先告知用户）

**二、执行中：心跳与自动停止条件**

| 条件 | 处置 |
|------|------|
| 成文每 ≤15s | 输出一行可见进度（同 S3 心跳原则） |
| 每章成稿后 | 立即写盘 + 更新 `.fbs/chapter-status.md` + 输出章内自审卡摘要 |
| 本编最后一章完成 | **主动停止**，生成 Auto-Run 完成报告（见 `large-scale-book-strategy.md §1b`） |
| 结构仲裁触发（每 20 章） | **暂停等待用户指令**（非自动继续）；将仲裁结果写入 `.fbs/structure-arbitration-log.md` |
| 限流预算 rateLimitRate > 0.6 | **立即暂停**，输出「检索成功率过低（{rateLimitRate}），建议等待 1–2 分钟后手动继续」 |
| 连续 3 章质量门禁未通过 | **暂停**，输出质量问题摘要，等待用户指令 |

**三、停止后：恢复话术**

| 场景 | 推荐话术 |
|------|----------|
| 正常完成一编 | 「第 X 编已完成（共 N 章），请查看 .fbs/auto-run-unit-report.md 确认质量状态后，继续第 X+1 编」 |
| 限流暂停 | 「因平台限流暂停（当前限流率 {X}%），已完成至第 N 章。建议等待 1–2 分钟后说「继续第 N+1 章」」 |
| 结构仲裁暂停 | 「已完成 {N} 章，触发结构仲裁。请查看 .fbs/structure-arbitration-log.md 并确认结构无漂移后说「继续写」」 |
| 质量门禁暂停 | 「连续 3 章质量未达标，已暂停。请查看各章 emergency-draft 并处理后说「继续」」 |

**禁止事项（全自动模式下）**：
- 禁止跨编连续写（每编写完须停止报告）
- 禁止在结构仲裁触发时静默跳过（必须暂停等待用户）
- 禁止在 rateLimitRate > 0.6 时继续发起检索（必须暂停）
- 禁止在台账新鲜度检测失败时直接开写（必须先补录台账）

### §3.3 单智能体串行写作质量底线（P0 强制，v1.9.0 新增）

> **来源**：2026-04-02 杜氏项目复盘——批量写作中存在三类系统性失效：台账状态全程未同步（P0-5）、部分章节字数严重低于目标未标注（P1-1）、分类型章节大量人物重复出现但未被检测（P1-2）。  
> **适用场景**：S3 单智能体串行模式（推荐模式），对每一章的执行约束。

---

#### §3.3.1 台账绑定写入（P0 强制，方案一）

> **根因**：章节正文写入磁盘与 `chapter-status.md` 状态更新依赖「模型记得执行」，两步之间无强制绑定，导致台账长期失真——正文已存盘，台账仍显示「❓ 待定」或「⏳ 进行中」。

**规则（P0 强制，视为一个原子操作）**：

```
每章写作完成后，必须在同一执行单元内完成以下两步：

Step 1：调用 write_to_file 将章节正文写入磁盘
        文件路径：{workspace}/[S3-ChNN] 第N章-标题.md

Step 2：立即更新 .fbs/chapter-status.md 对应行状态
        ├─ 正文已落盘 → 状态更新为 ✅ 已完成（若字数达标）
        │              或 ⏳ 骨架（若字数 < 目标 60%，见 §3.3.2）
        └─ 在同一轮工具调用中完成（非下一章开始时补录）

禁止：
  ❌ 正文已落盘但台账仍为 ❓ 待定 / ⏳ 进行中
  ❌ 将台账更新推迟到"全书写完后统一更新"
  ❌ 以"已在对话中说明完成"替代台账文件更新
```

**台账更新格式**（`.fbs/chapter-status.md` 对应行）：

```
| ChNN | {章节标题} | ✅ 已完成 | {实际字数}字 | {ISO时间戳} | {简要备注} |
```

**本规则不受用户"无需确认/持续执行"等授权语影响**（见 `SKILL.md` §v1.9.0 升级1 禁令D）。

#### §3.3.2 批量写作字数底线（P0 强制，方案五）

> **根因**：批量写作模式下，部分章节实际字数远低于目标字数（如目标2000字但实际仅600字），但台账仍标记为「✅ 已完成」，形成虚假完成状态，S6 报告中据此声明全书写作完成。

**规则（P0 强制）**：

```
每章正文写入磁盘后，立即执行字数达标检测：

Step 1：统计实际字数（含正文、小节标题、章节小结，不含 Chapter Brief）

Step 2：与 Chapter Brief 中的「字数目标」对比：

  ├─ 实际字数 ≥ 目标字数 × 80%
  │   → 台账状态：✅ 已完成
  │   
  ├─ 目标字数 × 60% ≤ 实际字数 < 目标字数 × 80%
  │   → 台账状态：⚠️ 待扩写
  │   → 在对话中输出：「本章字数 {实际} / 目标 {目标}（{比率}%），建议后续扩写」
  │   
  └─ 实际字数 < 目标字数 × 60%
      → 台账状态：⏳ 骨架
      → 在对话中输出：
        「⚠️ [骨架稿标注] 第{N}章实际字数 {实际}，
         低于目标字数 {目标} 的 60%（{比率}%）。
         已标注为骨架稿，建议扩写后方可纳入正式完稿统计。」
      → 章节文件头部增加标注：
        > ⚠️ 骨架稿 · 当前约{实际}字 / 目标{目标}字（{比率}%）
        > 建议扩写后移除本标注

禁止：
  ❌ 字数 < 60% 目标时，台账记为 ✅ 已完成
  ❌ 在骨架稿章节存在的情况下，S6 报告声明「全书写作完成」而不注明骨架章节列表
```

**S6 完结报告须同步骨架稿统计**（配合 §3.6 诚实完成度声明执行）：
- 存在骨架稿章节时，自动触发 §3.6 中 `⚠️ 骨架完成（待扩写）` 分级声明

#### §3.3.3 跨章去重检测（P1 建议，方案六）

> **根因**：分类型章节（如「按省分布」「历史名人」「族谱人物」等）中，不同章节容易重复叙述同一人物或同一地区的信息，导致读者体验割裂、内容价值下降。

**触发场景**：当 `[S2]目录草案.md` 或 `project-config.json` 中的 `genreTag` 包含以下类型时，本规则强制激活：
- 族谱类：`族谱/人物志/名人录/名人传/列传`
- 地理类：`分省/分地区/分县/各地/地域分布`
- 分类型：`各类/各期/各代/各朝/各编分类型章节`

**执行规则（P1 建议，M2/M3 项目升级为 P0）**：

```
分类型章节写作前（章前检索完成、Chapter Brief 输出后、正文成文前）：

Step 1：读取 .fbs/book-context-brief.md 中的「已写人物/地区/事件列表」
        （该列表由每章完成时更新，见 S3 多路并行写作「完成通知」规则）

Step 2：对比本章 Chapter Brief 中预计出现的人物/地区/事件：
  ├─ 无重叠 → 正常成文
  └─ 检测到重叠项 → 在 Chapter Brief 后输出：
  
    「⚠️ [跨章去重预警]
     以下人物/地区/事件已在前序章节出现：
     - {已出现项1}（首见：{章节编号}）
     - {已出现项2}（首见：{章节编号}）
     
     建议处理方式：
     A. 本章着重写「新角度/新信息」，交叉引用前章（推荐）
     B. 简述后以「详见第{N}章」指向前章
     C. 确认本章需要完整叙述（接受重复，用户知情）」
     
     请选择 A/B/C 后继续成文（默认 A）。

Step 3：每章完成后，更新 .fbs/book-context-brief.md 中的已写人物列表：
  追加本章新出现的人物/地区/事件（格式：{名称} | Ch{NN} | {一句简述}）
```

**`book-context-brief.md` 去重台账格式（追加节）**：

```markdown
## 已写人物/地区/事件清单（跨章去重台账）

| 条目名称 | 首见章节 | 一句简述 | 更新时间 |
|---------|---------|---------|---------|
| {人物/地区/事件} | Ch{NN} | {≤20字简述} | {ISO} |
```

#### §3.3.4 字数台账磁盘核验绑定（P0 强制，v2.0.0 新增）

> **来源**：2026-04-02 杜氏知识集质检复盘——`chapter-status.md` 字数字段为模型自报估算（"~4万"），无磁盘字符数核验，导致台账虚报字数与实际磁盘差距高达 4 倍以上（台账声称 166 万字，磁盘实测 35~40 万字）。  
> **根因**：台账更新规则（§3.3.1）要求同步更新状态，但未规定字数字段的数据来源必须为磁盘读取，模型使用写作时的主观估计填写字数。

**强制规则（P0，不受用户授权豁免）**：

```
台账字数字段写入规则：

1. 【首次写入】章节正文落盘后，须调用 read_file 读取该文件，
   统计实际字符数后写入台账，禁止使用写作时的主观估计：
   
   ❌ 禁止：| Ch01 | ✅ 已完成 | ~8000字 |     ← 主观估计
   ✅ 正确：| Ch01 | ✅ 已完成 | 8,234字（磁盘实测）|
   
2. 【批量补测】当台账字数字段存在估算值（含"~"符号）时，
   S5 终审或全书质检前须执行批量磁盘核验：
   逐章 read_file → 统计字符数 → 更新台账对应行

3. 【PowerShell 批量核验（有 Node/Shell 时）】：
   可使用以下命令批量获取所有章节字符数（Windows PowerShell）：
   
   Get-ChildItem "{书根}" -Filter "*.md" | 
     Where-Object {$_.Name -match "S3"} | 
     ForEach-Object { 
       "$($_.Name): $((Get-Content $_.FullName -Raw -Encoding UTF8).Length)字符"
     }

4. 【字数字段格式标准】（v2.0.0 起强制）：
   - 正确格式：{N}字（磁盘实测）或 {N}字符（磁盘实测）
   - 骨架稿：{N}字（磁盘实测，目标{M}字，{比率}%）
   - 含估算的旧格式须在下次更新时修正
```

**台账字段定义（更新 §3.3.1 中的台账格式）**：

```markdown
| 章节编号 | 状态 | 磁盘字符数 | 目标字数 | 达标率 | 备注 |
|---------|------|---------|---------|------|------|
| Ch01    | ✅ 已完成 | 12,456（磁盘实测）| 8,000 | 156% | |
| Ch02    | ⚠️ 骨架 | 1,234（磁盘实测）| 8,000 | 15%  | 需扩写 |
| Ch03    | ❌ 未开始 | — | 8,000 | 0% | |
```

> **质检等级速查**：🟢A（达标率≥70%）/ 🟡B（10%~69%）/ 🔴D（<10%）

```

#### 章前写作热身协议（G9，P2 建议）

> **设计来源**：人类写作质量模式 QM-4（渐进式写作与节奏控制）——职业写作者在开始长篇章节前，常先用 5–10 分钟做思维整理（outlining、freewriting 或边看前章结尾边记下本章关键词），使后续成文更流畅连贯。  
> **适用场景**：以下任一条件触发热身协议：跨会话开机后的第一章、连续写作超过 3 章后、上章质量门禁未通过后恢复。  
> **不适用**：时间敏感的快速续写（用户明确要求「直接写」）。

**热身步骤（3步，≤3 分钟）**：

```
章前热身（3步）：
  步骤1：读取上章 endHook（来自 .fbs/book-context-brief.md）
         → 用1句话默述：「上章结尾告诉读者：{X}，因此本章要接着说{Y}」
  步骤2：读取本章 Chapter Brief 中「核心主张」与「论述路径」
         → 对比 S2 目录中本章的描述，确认无偏差
  步骤3：输出热身宣告（可见于对话）：
         「即将开始第 N 章《{标题}》
          核心主张：{本章主张}
          本章承接：{上章 endHook 摘要}
          预计论述路径：{3–5步简述}」
→ 热身完成后立即进入章前检索（不再增加额外延迟）
```

**效果**：热身宣告可见于对话，让用户确认成文方向正确；同时帮助模型「激活」相关上下文，减少成文中途偏题。

> **token 成本估算**：热身步骤约消耗 200–300 token（主要是读台账和输出宣告），与其防止偏题节省的修订成本相比收益显著，建议默认开启。

#### 章节任务卡（Chapter Brief，按已选粒度执行，P0）

> **设计来源**：人类写作质量模式 QM-1（选题锁定）+ QM-2（分层大纲管理）——在动笔之前先形成结构化任务卡，是控制单章偏题的最有效手段。  
> **填写时机**：章前检索完成后、正式成文前；须存入 `.fbs/writing-notes/{chapterId}.brief.md`（由 `BookWorkflowOrchestrator._saveChapterBrief()` 自动写入，亦可由主 Agent 手动填写）。  
> **强制可见约定**：章前检索完成后，默认**禁止直接输出正文**。在 `briefGranularity=volume/chapter` 时，必须先在对话中输出对应 Brief 卡，等待用户确认或 **30 秒**默认通过后，方可进入成文；仅当用户显式确认 `briefGranularity=none` 时可跳过 Brief 卡。违反此约定视为 C1 结构问题。

#### Report Brief（B 级体裁等价物，P0 强制，v1.6.5 新增）

> **设计来源**：当体裁为「长篇报道/深度专题/调查特稿」等无章节结构的长文时，Chapter Brief 的触发条件（「章前检索完成后」）不会被命中，导致成文前缺乏结构锁定。Report Brief 是 Chapter Brief 在 B 级体裁下的等价机制。

**触发条件**：`genreLevel=B` 时，检索完成后、成文前必须输出 Report Brief。

**强制输出模板**：

```

**与 Chapter Brief 的对照**：

| 维度 | Chapter Brief（A 级） | Report Brief（B 级） |
|------|----------------------|---------------------|
| 触发 | 每章章前检索后 | 全文检索完成后（仅一次） |
| 结构 | 论述路径 3–5 步 | 结构路径（角度/段落） |
| 素材 | 按章分配 | 全文信源汇总 |
| 存盘 | `.fbs/writing-notes/{chapterId}.brief.md` | `.fbs/writing-notes/report-brief.md` |
| 确认 | 30秒默认通过 | 30秒默认通过 |

**禁止行为**：
- B 级体裁检索完成后，禁止跳过 Report Brief 直接成文
- Report Brief 中「信源状态」须如实反映检索深度等级（L1/L2/L3）

#### 最小成果先交付（B 级体裁 P0 强制，v1.6.7 新增）

> **根因**：审计发现模型在大规模联网核验后，仍未向用户交付任何可见写作产物（标题、导语、大纲、样段均未输出），用户感知为「查了很多，但什么也没写出来」。原因是工作流中没有一个「调研完成→先交付最小可见成果」的强制节点，导致交付被无限延后。

**触发条件**：B 级体裁的 S0-lite + S1 完成后（或起稿门槛已满足时），**必须**在 Report Brief 之前或同步输出「最小成果包」。

**最小成果包（Minimum Viable Deliverable, MVD）**：

```

📌 标题方向（3 个）：
  ① {标题1}（{角度说明}）
  ② {标题2}（{角度说明}）
  ③ {标题3}（{角度说明}）
  ★ 推荐：{推荐序号}

📝 导语（2 版）：
  【版本A · {风格标签，如"现象切入"}】
  {200-300字导语}

  【版本B · {风格标签，如"时间线切入"}】
  {200-300字导语}

📅 时间线骨架：
  {日期1} — {事件1}（来源：{F-ID}）
  {日期2} — {事件2}（来源：{F-ID}）
  …（≥8 个节点）

❓ 核心问题链（3-5 个）：
  Q1: {问题1}
  Q2: {问题2}
  Q3: {问题3}

  一、{节标题}（预计 {N} 字）— 证据：{F-ID}

回复「OK」「选标题N」「调整大纲」或直接说修改意见。

```

**存盘**：`{workspace}/[S1] 最小成果包.md`（B 级体裁，P0 强制落盘）

**与 Report Brief 的关系**：MVD 是面向用户的「我要写什么」预览；Report Brief 是面向模型执行的「我怎么写」锁定。MVD 通过后，其标题/大纲/时间线直接灌入 Report Brief 对应字段。

**禁止行为**：
- 起稿门槛满足后，禁止跳过 MVD 直接输出 Report Brief
- MVD 中的时间线须引用证据台账中的事实 ID
- 导语须基于已检索验证的事实，禁止凭模型知识编造开头

#### 局部先写机制（B 级体裁 P1 建议，v1.6.7 新增）

> **根因**：审计发现模型将「成文」理解为「全部核验完成后一次性写完全文」，但优秀的报道写作应该是「边核边写」——某个主题块证据足够时，先产出该段落，而非等待所有信息到齐。

**原则**：当 B 级体裁的某个「一级小节」满足以下条件时，**允许且鼓励**先行产出该段落：

```
局部先写触发条件（每节独立判断）：
  ├─ 该节在证据台账中有 ≥2 条 L2 级事实 → 可先写
  ├─ 该节时间线节点已锁定 → 可先写
  └─ 该节不依赖其他未完成节的结论 → 可先写
  
  满足以上 3 条中的前 2 条 → 建议先行产出该段落
```

**局部段落命名**：`[草段] {节标题}.md`

**流程**：
1. 产出局部段落 → 对话中输出 + 存盘为草段文件
2. 继续后续小节的检索/核验
3. 全部段落完成后，合并为完整初稿 → Report Brief 确认 → 统稿

**适用体裁模块划分建议**（追踪报道典型结构）：

| 模块 | 可独立先写条件 | 说明 |
|------|---------------|------|
| 现象段 | 有媒体报道 + 用户反应素材 | 通常最先可写 |
| 版本/产品演进段 | 有官方发布页 + GitHub 记录 | 事实密度高，适合先写 |
| 平台响应段 | 各平台动作已核实 | 多信源交叉验证后可写 |
| 含义判断段 | 依赖前三段事实 | 通常最后写 |
| 风险与未来段 | 有争议点矩阵 | 可与含义段并行 |

**禁止行为**：
- 局部先写不等于降低质量标准——每个草段仍须满足最小自审中的「S 层」和「数据与引用」要求
- 草段合并为全稿后，仍须执行完整的最小自审检查单

### §3.4 S4 大体量合稿策略（P0 强制，v1.9.0 新增）

**规则（P0 强制阻断，M2/M3 项目必须执行）**：

  - 已完成章节数（✅ 状态）
  - 已完成章节总字数（各章字数之和）

Step 2：若满足以下任一条件，触发大体量合稿策略：
  ├─ 总字数 ≥ 20 万字（M2/M3 项目）
  └─ 已完成章节数 ≥ 30 章

**合并脚本模板（Windows .bat）**：

```batch

    echo. >> %OUTPUT%
)

echo [S4] 合稿完成：%OUTPUT%
```

### S4 排版构建：防卡顿（体验强约束）

> **现象**：进入 S4 后长时间无消息——常见于 **`node assets/build.mjs`**：依赖安装、**Chromium 冷启动**、`page.setContent` 使用 **`networkidle0`（最长约 90s）**、**Mermaid CDN 渲染等待（最长约 45s）**、大书 **DOCX 转换**；会话内若由模型代跑 Bash，用户看不到终端输出时更易误判「卡死」。

| 根因 | 模型 / 宿主须落实 |
|------|-------------------|
| 本地构建长静默 | 在发起 `node …/assets/build.mjs` **前**向用户说明：将经历「解析 MD → 写 HTML →（可选）PDF/DOCX」，PDF 阶段可能 **数十秒无新输出**；建议用户同时看终端或日志。 |
| 终端有输出但对话无 | `build.mjs` 会输出 **`[S4/build][书id]`** 前缀进度行；模型可将终端尾部 **摘要贴回对话**（每 **≤30s** 或每完成一书），与 `SKILL.md` §1 心跳一致。 |
| 规范冷读 | 进入 S4 **首轮**避免无说明地 **Read 超过 3 份长文档**；`typography` / `build.md` 按需 **节选** 或引用 skill-index 短链。 |
| 仅要 MD | 若用户只要成稿 MD，**不必**强跑 Puppeteer；避免为「完整构建」而拉长无反馈时间。 |

**代码侧**：`assets/build.mjs` 已在关键步骤打印 `[S4/build]` 进度；集成宿主可选解析该前缀驱动 UI 进度条。

## 阶段5：质量终审

### §3.5 S5 终审执行约束（P0 强制，v1.9.0 新增）

> **来源**：2026-04-02 杜氏项目复盘 P0-2——S5 终审报告未读取任何章节文件即输出"综合评分 8.6/10，全部通过"，属零读取自评，对用户形成质量误导。  
> **根因**：用户授权"无需确认/持续执行"时，S5 退化为形式性文档生成，而非真实审校。

**强制规则（P0，不受用户授权豁免）**：

```
S5 终审报告必须包含以下可验证的真实执行记录：

1. 【实际读取清单】
   列出本次 S5 中实际执行 read_file 的章节文件：
   - 最低覆盖率：总章节数的 20%（如 50 章项目须抽查 ≥10 章）
   - 格式：「已读取：ch-XX（{字数}字）、ch-YY（{字数}字）……」
   
2. 【实际发现问题】
   列出抽查章节中发现的实际问题（允许为零，但须注明）：
   - 零问题时：「已读取以下 N 章，未发现结构性问题：[列表]」
   - 有问题时：逐条列出，不得合并为「总体良好」
   
3. 【未覆盖章节声明】
   若全书章节数 > 10 章，须声明：
   「以下章节未在本次 S5 中审校：[列表]
    建议出版前补充抽查上述章节」

4. 【完成度诚实声明】
   - 若全书有骨架稿章节（⏳ 状态）：
     「⚠️ 本书含 N 章骨架稿（未达字数目标），
      不建议声明"全书质量终审通过"」
   - 若附录有"待补充"项：
     「⚠️ 以下附录内容未完成：[列表]」

禁止：
  ❌ 在零读取的情况下输出"全部通过"的终审评分
  ❌ 声明"已完成全书质量终审"而实际覆盖率为 0
  ❌ 对含骨架稿的书籍声明"出版级终稿"

本约束不受用户"无需确认/持续执行"等授权语影响
（见 SKILL.md §v1.9.0 升级1 禁令C）。
```

**大体量项目（M2/M3）S5 分轮执行策略**：

```
当全书章节数 ≥ 30 章（M2/M3）时，S5 终审须分轮执行：

第一轮：抽样审校（20%覆盖，输出初审报告）
  → 宣告：「本轮 S5 为抽样审校，覆盖率 20%（N章/共M章）」
  
第二轮（可选，用户要求时）：补充覆盖剩余章节
  → 每轮最多审校 10 章，避免上下文溢出
  
终审声明须注明实际覆盖率：
  「本次 S5 终审：抽样覆盖率 {X}%（{N}章/共{M}章）
   完整覆盖率需 {轮数} 轮，已完成 {已轮数} 轮」
```

### §3.5.1 S5 质检抽样率量化约束（P0 强制，v2.0.0 新增）

> **来源**：2026-04-02 杜氏知识集质检复盘——S5 终审声称"覆盖全书"但实际零读取；§3.5 已规定"20% 覆盖率"，但无量化执行约束，导致该规定形同虚设。  
> **根因**：抽样率要求仅为文字描述，无强制执行节点与输出格式要求，模型可在未读取任何文件的情况下绕过。

**强制规则（P0，不受用户授权豁免）**：

```
S5 终审启动时，须在对话中输出抽查计划声明（P0 阻断门禁）：

━━━━━━ 📋 S5 抽查计划 ━━━━━━
全书章节总数：{M} 章
最低抽查数量：{ceil(M×0.2)} 章（≥20%）
本次计划抽查：{N} 章（列出章节编号）
抽查覆盖率：{N/M×100}%
━━━━━━━━━━━━━━━━━━━━━━━━━

禁止：
  ❌ 未输出抽查计划即直接输出终审报告
  ❌ N < ceil(M×0.2)（抽查章节少于 20% 总量）
  ❌ 计划中列出的章节与实际读取的章节不一致（须执行 read_file，不得凭记忆）
```

**抽查执行记录格式（每章读取后逐条输出）**：

```
✅ 已读取：[S3-ChNN] 第N章.md | 磁盘字符数：{chars} | 关键问题：{无/具体问题}
```

**最低抽查数量计算规则**：

| 全书章节数 | 最低抽查章节数 |
|-----------|------------|
| ≤10 章 | 全部（100%） |
| 11–20 章 | ≥4 章（≥20%，向上取整） |
| 21–50 章 | ≥ceil(M×0.2) 章 |
| ≥51 章 | ≥10 章（上限，但须覆盖各编至少 1 章） |

> **多编结构要求**：全书分多编时，每编须至少抽查 1 章，不得集中抽查同一编。

### §3.6 S6 诚实完成度声明（P0 强制，v1.9.0 新增）

> **来源**：2026-04-02 杜氏项目复盘 P1-4——9 种附录中有 3 种标注"待补充"，但 S6 报告将其全部列入"已完成"产出物清单，形成虚假完整性声明。  
> **根因**：S6 报告生成时无完成度分级要求，模型倾向于将"已生成文件"等同于"已完成内容"。

**强制规则（P0，不受用户授权豁免）**：

```

  ✅ 完整达标：
    文件存在 + 实际字数 ≥ 目标字数 × 80% + 无"待补充"标注
    
  ⚠️ 骨架完成（待扩写）：
    文件存在 + 实际字数 < 目标字数 × 60%，或含"待补充"标注
    须在条目后注明：「需扩写至 {目标字数}，当前约 {实际字数}」
    
  🔄 部分完成：
    文件存在但内容明显不完整（仅有标题框架，无实质内容段落）
    
  ❌ 未完成：
    文件不存在

全书完成度须以百分比声明（格式强制）：
  「正文完成度：{X}%（{A}章完整达标 / {B}章骨架 / {C}章未完成）
   附录完成度：{X}%（{A}种完整 / {B}种骨架待补充 / {C}种未完成）
   整体项目完成度：{X}%（含骨架稿为部分完成）」

禁止：
  ❌ 将"待补充"项目列入"已完成"清单
  ❌ 在完成度 < 80% 的情况下输出"项目圆满完结"类声明
  ❌ 将骨架稿（⏳ 状态）视为等同于完整达标（✅ 状态）

（见 SKILL.md §v1.9.0 升级1 禁令E）。
```

## 时间标签检查单（v1.8.0，P0）

> **问题根源**（审计07）：`temporalAccuracy` 条文完备，但无强制触发检查节点——S0 时间戳检索无阻断、hardcode 年份拦截从未生效（「2025年后」重复4次未检测到）。P0合规率约25%。

### S0 时间基准门禁（P0 强制，阻断进入 S1）

S0 的**第一个动作**须执行时间基准检索，结果必须写入简报首行：

```
[S0 时间基准检索] WebSearch「今天是哪年哪月哪日」
→ 结果写入 [S0] 调研简报首行：「**时间基准**：YYYY年MM月DD日（来源：WebSearch）」
→ 无「时间基准」行则阻断进入 S1

同时写入 search-ledger.jsonl：
{
  "kind": "search",
  "query": "今天是哪年哪月哪日",
  "s0Dimension": "timestampCheck",
  "yearSourceConfirmed": true,
  "result": "YYYY年MM月DD日",
  "timestamp": "{ISO}"
}
```

### 正文年份核实流程（P0 强制）

每次正文中出现4位数字年份（如「2025年」「2026年」）时：

1. **先查账本**：`search-ledger.jsonl` 中是否存在该年份相关检索（`yearSourceConfirmed=true`）
2. **有来源**：可写入，须标注 `〔来源：{来源名}〕`
3. **无来源**：须先执行 WebSearch 核实，或标注 `〔年份待核实〕`，**禁止以训练记忆填充**

### 季度精度要求（P1）

「Q1/Q2/Q3/Q4」等季度表述须补充具体月份，否则标注 `〔季度范围，具体月份待核实〕`：
- ✅ 「2026年3月27日」
- ✅ 「2026年Q1（1月–3月）」
- ❌ 「2026年Q1」（缺具体月份，模糊）

### 与 search-policy.json 的对应关系

| 规范字段 | 本节等价执行步骤 |
|---------|---------------|
| `temporalAccuracy.requireTimestampSearchAtS0` | S0第一步执行时间基准检索 |
| `temporalAccuracy.hardcodeYearDetection` | 正文年份核实流程第1步查账本 |
| `searchEnhancement.freshKeywordInjection.forbiddenSuffixes` | 检索 query 禁用 4 位数字年份前缀 |
| `temporalAccuracy.yearLabelPolicy: search_before_write` | 先有账本记录再写入年份 |

## §3.7 全书质检执行规范（P0 强制，v2.0.0 新增）

> **来源**：2026-04-02 杜氏知识集全面质检复盘——本次质检暴露的核心问题：质检过程本身缺乏标准化 SOP，导致"质检已完成"声明与"实际执行内容"严重脱节（台账虚报 4 倍字数、S5 零读取评分、骨架稿被标记为已完成）。  
> **核心原则**：**以磁盘真值为质检唯一基准**，禁止以"模型记忆"替代"磁盘读取"作为质量判断依据。

### §3.7.1 禁令 F：禁止零磁盘扫描的质检声明（P0 铁律）

```
以下声明，在未执行磁盘文件读取/扫描的情况下，视为无效声明：

禁止无效声明类型：
  ❌ "全书终审通过，综合评分 X/10"（未读取任何章节文件）
  ❌ "全书共 N 万字，已完成写作"（字数来自模型估算）
  ❌ "以上章节质量良好，无明显问题"（未打开任何文件核查）
  ❌ "chapter-status.md 已更新至最新状态"（未经磁盘核验直接声明）

有效声明要求：
  ✅ 声明须附实际读取/扫描的章节列表及字符数
  ✅ 字数声明须附磁盘扫描结果（精确到字符）
  ✅ 覆盖率声明须附已读 vs 未读章节对照表

本禁令不受用户任何授权语影响（属 P0 铁律，见 SKILL.md §v1.9.0 升级1）。
```

### §3.7.2 全书质检 SOP（标准执行流程）

> **适用场景**：用户要求"全面质检"/"质检报告"/"检查全书质量"时，按本 SOP 执行。

```
全书质检标准执行流程（共五步，缺一不可）：

━━━━━━ 全书质检 SOP ━━━━━━

Step 1：磁盘文件完整性核查
  - 列出本书根目录下所有章节文件（list_dir 或 Glob）
  - 统计每个文件的字符数（read_file + len 统计，或 PowerShell 批量）
  - 输出：文件清单表（文件名 | 字符数 | 是否存在）
  - 发现缺失章节文件须标注 ❌

Step 2：内容质量抽样读取（≥20% 章节）
  - 按编次均匀抽样（每编至少 1 章）
  - 对每章执行 read_file 并进行 S/P/C 层快速扫描
  - 记录：章节编号 | 磁盘字符数 | 关键发现（问题或无问题）

Step 3：跨章一致性核查（CX 精简版）
  - CX-1：人物/事件论断是否有矛盾（各编各取 1 章对比）
  - CX-2：同一数据多章出现时口径是否一致
  - CX-4：是否有章节完整复述另一章内容（重复论述检测）
  - 特别检查：分类型章节（名人传/省域）的人物跨章重叠

Step 4：台账 vs 磁盘一致性核查
  - 读取 .fbs/chapter-status.md
  - 对比台账记录状态 vs 磁盘实际字符数
  - 发现台账字数虚报（估算值 vs 实测差距 > 50%）须标注 ⚠️
  - 发现台账状态与磁盘实情不符须标注并列入修正建议

Step 5：生成质检报告并落盘
  - 使用 §3.7.3 标准模板
  - 写入 .fbs/writing-notes/质检报告-{日期}.md
  - write_to_file 后执行 read_file 验证（§3.X.1）
  
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### §3.7.4 质检后台账修正规则（P0 强制）

```
全书质检执行后，须同步修正台账：

1. 将台账中使用估算字数（含"~"符号）的行，
   替换为磁盘实测字符数（格式：{N}字符（磁盘实测））

2. 将台账中状态与磁盘实情不符的行进行修正：
   - 磁盘字符数 < 目标×60%，但台账标注"✅ 已完成"
     → 改为 "⚠️ 骨架稿" 并标注字数和比率

3. 台账修正后执行 read_file 验证（§3.X.1）

4. 在质检报告中记录台账修正动作：
   「已修正台账 {N} 行：{列表}」
```
